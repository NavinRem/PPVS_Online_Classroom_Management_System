# AI Agent Workspace Rules (`GEMINI.md`)

This document defines the **mandatory global rules and architectural standards** for any AI agent (e.g., Antigravity, Gemini) working on the **PPVS Online Classroom Management System** workspace. All AI assistants must strictly follow these rules to maintain code consistency, type safety, and architectural accuracy.

---

## 1. Mandatory Workflow & Planning Discipline

1. **Plan Before Execute (`plan before execute`)**: For any non-trivial architectural change, multi-file refactor, or new feature request, the agent **must** create or update `implementation_plan.md` and obtain explicit user approval before modifying code files.
2. **Documentation & Integrity**: Never delete or strip existing docstrings, comments, or error handlers unrelated to the immediate task.
3. **Monorepo Integrity**: This project is a unified monorepo (`backend/`, `frontend/`, `docker-compose.yml`, `firebase.json`) tracked by a single Git repository (`/.git`). **Never** initialize nested `.git` directories inside `backend/` or `frontend/`.
4. **Respect Intentional User Deletions (`no unsolicited re-adding`)**: If the user explicitly deletes or strips out certain code, comments, docstrings, or frontend styling, the AI agent **must never automatically rewrite or re-insert** what the user removed. Always strictly respect the user's manual deletions across both frontend and backend.
5. **Centralized & Categorized Documentation (`docs/` root folder)**: All technical documentation, engineering guides, architectural references, and test explanations **must** be stored inside the root `docs/` folder (`/docs/`), categorized neatly into subfolders based on content type (e.g., `docs/backend/`, `docs/testing/`, `docs/api/`, `docs/frontend/`). Never scatter or leave `.md` documentation files inside subproject folders (such as `backend/docs/`).
6. **Immediate Prettier Formatting (`instant formatting`)**: Whenever any code file (`.ts`, `.js`, `.json`, `.css`, etc.) is written, modified, or generated by the AI agent, the agent **must immediately apply Prettier formatting** (`npx prettier --write <filepath>` or `npm run lint`) right after creating or editing the file. This guarantees that zero unnecessary red underlines or formatting lint warnings appear in the user's IDE.
7. **System-Wide CamelCase Naming (`camelCase policy`)**: All variable names, function names, method names, class properties, and data/DTO/Firestore keys across the system (`backend/` and `frontend/`) **must** strictly use `camelCase` (e.g., `verifyTeacherClassOwnership`, `studentId`, `createdAt`). Never use `snake_case` or `PascalCase` for local variables, properties, or functions.
8. **Feature Implementation Checklist, Progress Tracking & Mandatory Walkthrough (`checklist & walkthrough rule`)**: Whenever starting or working on any feature or task:
   - **Generate Checklist**: The AI agent **must** generate a comprehensive action checklist (`task.md` and/or `implementation_plan.md`) listing all necessary steps and what needs to be done (`[ ] uncompleted`).
   - **Track Progress Continuously**: As implementation proceeds, the agent **must actively track and update the checklist status** (`[/] in progress`, `[x] completed`) so progress and current status are always visible.
   - **Mandatory Walkthrough at Completion**: At the conclusion of implementation, the agent **must always generate a comprehensive `walkthrough.md`** as the final result, summarizing what was accomplished, files changed, validation results, and checklist progress status.
9. **Post-Walkthrough Final Diagnostics & Verification Audit (`final verification audit rule`)**: After generating or updating the final `walkthrough.md`, the AI agent **must** run a final verification check across the codebase (`ng build` / `npm test` / diagnostics check) to guarantee there are zero missing imports, wrong syntax errors, broken links, or unhandled compilation issues remaining.
10. **Strict Real Features Only — No Demo Drawers or Mock Fallback UI (`no demo features rule`)**: The AI agent **must never add demo features, mock login buttons, quick unlock drawers, or simulated test fallbacks** (`quickDemoLogin`, `demoDrawer`, etc.). Only implement the real, production-ready required features. The user will manually test UI rendering and feature flows directly.
11. **Auto-Close Status & Error Messages (`auto-close messages rule`)**: Whenever any global styled error, warning, or status message (`AlertMessageComponent` or toast) is displayed to the user across any component, the application **must automatically close or dismiss the message after a few seconds** (e.g., 5 seconds) to prevent stale messages from lingering on the screen, while also allowing manual dismissal (`×`).
12. **Mandatory Explicit Error Handling (`no empty try-catch rule`)**: Whenever `try/catch` is used in TypeScript, JavaScript, or any code block across the frontend or backend, **never leave the `catch` block empty** (`catch {}`). Every `catch` block **must** explicitly handle, log (`console.error`, `console.log`, or dedicated logger), or re-throw the caught exception so that errors and failures are never swallowed silently without visibility.

## 2. Backend Rules (NestJS + Firebase Firestore)

### A. Strict TypeScript (`no any` Policy)

- **Never use `any`**. All DTOs, service payloads, and interfaces must use strict typing, classes, or `Record<string, unknown>`.
- When converting TypeScript class instances (`CreateDto`, `Partial<CreateDto>`) to `Record<string, unknown>` for Firestore formatting, always cast through `unknown` first (`data as unknown as Record<string, unknown>`) to prevent `TS2352` index signature compilation errors.

### B. Blueprint Service Architecture (`FirestoreBaseService<T>`)

- Every domain module service (e.g., `UsersService`, `PaymentsService`, `AssessmentsService`, `AttendanceService`, `SessionsService`, `NotificationsService`, `EnrollmentsService`, `ClassesService`) **must inherit from `FirestoreBaseService<T>`** (`src/common/firebase-base.service.ts`).
- **Template Hooks**: Always use the protected formatting hooks provided by `FirestoreBaseService<T>`:
  - `formatCreatePayload(data, auditContext)`: Automatically attaches `createdAt`, `createdBy`, `updatedBy`.
  - `formatUpdatePayload(data, auditContext)`: Automatically attaches `updatedAt`, `updatedBy`.
  - `formatResponse(id, data)`: Wraps Firestore document data with its string `id`.
- Do not duplicate standard `findAll()`, `findOne(id)`, `update(id, data)`, or `remove(id)` implementation logic inside child services unless adding domain validation or custom queries.
- **Centralized Shared Logic & DRY Rule**: Whenever a utility function, profile lookup (`findByUid`), or RBAC verification logic (`verifyTeacherClassOwnership`, `verifyStudentAccess`) is used across multiple modules (`src/modules/*`), it **must** be centralized inside the `src/common/` folder (e.g., inside `FirestoreBaseService<T>` (`src/common/firebase-base.service.ts`) or dedicated helper utilities in `src/common/`). Never duplicate helper or query logic across child module services.

### C. Standardized Controller & Module Requirements

- Every backend module **must** be registered in `src/app.module.ts`.
- Every backend module **must** have a dedicated `update-*.dto.ts` file extending `PartialType(CreateDto)`.
- Every controller **must** expose complete CRUD endpoints (`GET /`, `GET /:id`, `PATCH /:id`, `DELETE /:id`) guarded by `FirebaseAuthGuard` and `RolesGuard`, alongside any domain-specific workflow endpoints (`/check-in`, `/checkout`, `/grades`, etc.).

### D. Application Startup (`main.ts`)

- **Never use `void bootstrap();`**.
- Always use `.catch()` promise error handling around `bootstrap()` to log fatal startup exceptions and exit cleanly with code `1`:
  ```typescript
  bootstrap().catch((error: unknown) => {
    console.error("Fatal error during NestJS application startup:", error);
    process.exit(1);
  });
  ```

### E. Audit Logging

- Data mutations (`CREATE`, `UPDATE`, `DELETE`, `STATUS_CHANGE`) must record audit trails using `AuditLogsService.logAction(...)`.
- Pass `AuditContext` (`{ uid: string; role?: string; name?: string }`) from the authenticated request object (`req.user`) to ensure complete tracking of modification history.

### F. Strict DRY, Module Delegation & Anti-Duplication Rule

- **Zero Duplication of Files, DTOs & Helper Methods**: Never duplicate DTO structures, interfaces, models, or query helpers across modules. If a DTO or interface is shared between multiple modules (`AuthModule`, `UsersModule`, `AuditLogsModule`), it **must** be centralized inside `src/common/` or cleanly imported from its primary module.
- **Strict Module Boundaries (`Separation of Concerns & Delegation`)**: A module must never duplicate queries or directly manipulate Firestore collections owned by another module. For example, `AuthService` must never directly read or write to the `users`, `parents`, `students`, or `teachers` collections using raw Firestore calls (`this.firebase.firestore.collection(...)`). Instead, `AuthModule` must import `UsersModule`, `ParentsModule`, `StudentsModule` and strictly delegate data operations to their exported services (`UsersService.createOrUpdateUser()`, `ParentsService.createOrUpdateProfile()`, `StudentsService.create()`).
- **Orchestration vs. Domain Storage**: Orchestration modules (`AuthModule`) only coordinate multi-step workflows (such as credential verification and initial registration dispatch). They must never act as domain storage controllers for entities managed by separate domain modules.

## 3. Business Domain Standards

1. **Currency (Cambodian Riel - `KHR`)**:
   - All invoices, tuition payments, checkout flows, and monetary calculations must use **Cambodian Riel (`KHR`)** as the active currency. Do not default to USD.
2. **Attendance Statuses**:
   - Attendance records must strictly support the four customized statuses:
     ```typescript
     "present" | "homeworked" | "permission" | "absent";
     ```
   - The system tracks not only absence or physical presence (`present`), but specifically distinguishes students who came to class and completed homework (`homeworked`) and those on approved leave (`permission`).
3. **Role & Visibility Boundaries**:
   - **Admins (`admin`)**: Act as school Principal. Have unrestricted CRUD and full visibility across every data record, profile, and collection across the system without limitation.
   - **Teachers (`teacher`)**: Can record grades, batch check-in attendance, create class sessions/materials, and view metrics strictly for classes assigned to them (`classData.teacherId === requesterUid`), and view student profiles/scores only for students enrolled in their assigned classes.
   - **Students (`student`)**: Can only view their own class sessions/materials (for enrolled classes), their own scores/grades, and their own attendance/enrollment records (`requesterUid === studentId`).
   - **Parents (`parent`)**: Can only view their own profile and their own children's (`student.parentId === requesterUid`) academic summaries, attendance histories, schedules, and invoices.

## 4. Frontend Rules (PWA / Web Application)

- **Aesthetics & Experience**: Prioritize modern, high-contrast, premium UI design (rich color palettes, smooth micro-animations, glassmorphism, responsive layouts).
- **Offline / PWA Capable**: Ensure mobile and tablet interfaces work reliably as Progressive Web Apps for parents, teachers, and students.
- **Centralized Components & Styling (`shared architecture`)**:
  - **SCSS over Tailwind for Clean Templates**: Use modular SCSS (`styleUrl: './component.scss'`) with centralized design tokens rather than utility-heavy Tailwind inside Angular templates. This keeps component HTML templates clean, readable, and perfectly aligned with Angular's native view encapsulation (`@Component({ styleUrl })`).
  - **Shared Style Tokens & Mixins (`src/app/shared/styles/` & `src/styles.scss`)**: All global design variables (colors, typography, spacing, border radii, glassmorphism shadows) and mixins **must** be centralized in `src/app/shared/styles/` (e.g., `_variables.scss`, `_mixins.scss`). Component `.scss` files should import and call these tokens and mixins by name instead of hardcoding hex colors (`#6366f1`) or redundant layout definitions across individual files.
  - **Shared Reusable Components (`src/app/shared/components/`)**: Any reusable UI element, badge, modal, status indicator, or card structure used across multiple views or features **must** be placed in `src/app/shared/components/` so it is easily discoverable and avoids code duplication.
  - **Mandatory Global Styled Error & Validation Messages (`always send global style designed message`)**: Whenever any form submission, API call, or input validation occurs on the frontend, the app **must always send and display a globally styled, premium error or status message** (e.g., styled alert boxes or toast notifications using shared design tokens (`alert-error`, `alert-success`)) when there is an error or missing required input across all components. Never use browser default `alert()` or unformatted raw text.
